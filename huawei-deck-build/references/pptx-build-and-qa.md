## 1. 引擎解析

构建开始时运行 `scripts/check-environment.mjs --json`，按 `engine-routing.md` 在 `artifact-tool` 与锁定版本 PptxGenJS 中选择一次。整套 PPT 只使用该适配器，不混用、不现场派生新引擎；所选引擎、检测依据与能力等级写入 `qa-report.md`。

视觉路线二选一，任何引擎下通用：

- 需要精确复刻官方模板时，使用 `assets/huawei-refs/官方PPT模板-浅色16-9.pptx` 作为参考模板，走所选引擎的模板跟随流程；
- 否则从零构建，华为风作为显式自定义视觉方向传入（以 `visual-system.md` 为准），不使用引擎默认装饰主题。

## 2. 中文字体

- 构建与渲染前运行 `bash scripts/setup-fonts.sh --verify`；字体已预解压至 `assets/fonts/otf/`，脚本负责生成任务级 Fontconfig 并校验解析结果。需要为子进程注入字体环境时，用 `bash scripts/setup-fonts.sh -- <command>` 或将其输出的 `FONTCONFIG_FILE` 传给渲染进程。
- 宿主无 fontconfig（如未装 fontconfig 的 macOS）时，脚本降级为验证字体文件完整性并提示；渲染检查可使用操作系统的已验证 CJK 管线，并在 `qa-report.md` 记录声明字体与实际渲染字体。
- PPTX 内中文字体声明始终使用 `Noto Sans CJK SC`。
- 任何引擎下，中文都不得以拉丁字体回退渲染；发现回退即停止并修复字体链路，不带着错误继续排版。

## 3. 原生实现规则

载体选择、表格与图表规则、页面骨架、语义分组原则遵循 `visual-system.md` §4–6、§8；本节只规定构建层额外要求。

- 全部内容为原生可编辑对象；禁止把整页或整个功能模块渲染为图片。位图仅用于截图、照片等本质图像内容，或难以用原生对象复现的来源。
- 语义模块组成原生 Group Shape：每个可分组成员使用稳定唯一的形状名，按从后到前顺序连续创建。引擎不支持原生分组时，导出中间 PPTX 后用补丁脚本后处理：

```bash
node scripts/patch-pptx-grouping.mjs --input intermediate.pptx --output final.pptx --groups semantic-groups.json
```

`--groups` 参数的 JSON 成员格式示例：

```json
{
  "slides": [
    {
      "slide": 1,
      "groups": [
        {
          "name": "KPI card: active users",
          "members": ["KPI_BG", "KPI_TITLE", "KPI_VALUE", "KPI_UNIT"]
        }
      ]
    }
  ]
}
```

补丁工具根据成员变换推导分组边界，将成员保留为原生可编辑对象，移除 `noGrp` 与 `noUngrp` 锁，并输出命名空间完整的 `<p:grpSp>` 标记。保持 JSON 成员关系明确，不要仅凭几何邻近猜测分组。

- 不要将整页、无关的相邻模块，或需要独立动画或重复对齐的对象分组。保持组合边界与用户预期会作为一个单元去选中、移动、复制、缩放或删除的含义一致。
- 当原生分组确实无法生成时，保持每个组件可独立编辑，具有干净的边界与合理的堆叠顺序，以便用户在 PowerPoint 中选中、组合、取消组合并修订模块。
- 清除独立可编辑对象的 `noGrp` 锁和自建分组的 `noUngrp` 锁。某些 PowerPoint 生成路径会输出 `<a:spLocks noGrp="1">`，即使对象看起来可编辑也会禁用"组合"命令；将任何残留的分组锁视为阻断交付的缺陷。交付前在成品 XML 中校验 `<p:grpSp>` 数量与预期一致、无残留分组锁，并用严格 Open XML 读取器重新打开成品。
- 来源：页内短来源，备注 `[Sources]` 块完整链接与口径；讲解稿写入备注。
- 人工待补项实现为原生可替换模块：截图预留位保留预期比例、界面语境和标注区域；数据结构已知时先建原生表格/图表骨架。页内显示稳定 ID 和简短插入说明，完整责任、格式、用途、阻断级别和到位后动作写入备注或交付清单。存在占位项时，依赖它的标题、数字或推荐不得以最终结论形式呈现。

## 4. 容量预检

逐页生成前，对该页按 `page-script.md` 视觉轴和 `slide-plan.json` 几何自动检查（无论后续是全稿直出还是样页抽样，每页生成前都先过预检）：

- 标题长度与预期行数（单行设计不得换行）；
- 文本字符量、表格行列数、最长单元格；
- 页脚与来源安全区是否被侵占；
- 按下限字号（`visual-system.md` §2 token 表）能否容纳全部内容；
- 公司名、产品名、URL、数字+单位是否可能异常断行（受保护文本见 `visual-system.md`）；
- 截图或图表是否保留足够可读区域；
- 页面是否同时承担两个独立叙事任务。

预检失败时按顺序处理：删除重复表达与无效修饰 → 改用更高效的原生表格/图表/流程 → 调整列宽、区域比例和来源写法 → 次要明细移入附录 → 按该页已确认的超载规则拆页 → 仍需改变已确认方案时返回用户确认。任何一步都不使用低于下限的字号或机械断词。

## 5. 样页策略（内部验证）

高风险样页是 Agent 内部工程验证手段，不向用户请求确认：

- 8 页以内的短报告：逐页预检后直接生成全稿初版，再统一进入五轮 QA；
- 8 页以上或结构复杂的报告：按"版式家族"抽样——至少覆盖最密表格、复杂架构/流程、图表、截图和特殊占位中实际出现的高风险类型，不按固定页码机械选 2—3 页；
- 样页验证字号、信息密度、原生载体、分组、来源和占位替换方式，通过后将已验证规则铺开全稿；
- 只有样页证明已确认方案在下限字号、既定页数或原生载体下不可实现，且必须改变信息、结构或页数时，才返回受影响页面请用户决定。

## 6. 五轮独立 QA

分五轮独立执行，不以一轮浏览代替。任何一轮不通过都不得交付。A—D 轮逐页检查，E 轮在整套 deck 渲染后整体检查。

### A. 内容一致性

- 页面标题、正文、数据、表格字段、备注与双轴逐字稿一致；构建前从 `page-script.md` 导出每页"允许出现的文字集合"，构建后从 PPTX 提取文本对比——标点、断行和经记录的等义压缩允许存在，任何新增结论、数字或品牌名必须阻断交付；
- 未新增研究结论或宣传式升级；
- 标题序列仍构成完整论证，页间承接和建议映射一致。

### B. 可读性与视觉语义

- 无需备注即可理解；阅读顺序与视觉结构一致；
- 关键数字、结论和边界未在构建中丢失；载体与信息关系匹配；
- 无重复标题的结论条、无效卡片墙或装饰性结构；
- 截图、图表和来源在 100% 显示下可读。

**页型级补充检查**（按该页所选页型，追加以下对应项）：

| 页型 | 检查项 |
|---|---|
| 前后对比 | 左右/上下两栏视觉平行——同等高度、同等条目数；AS-IS 与 TO-BE 用颜色或标签区分 |
| 竞品对比 / 方案决策 | 表头行深色白字；推荐方案或关键行高亮反色；列宽足够，无单元格 3 行+换行 |
| 能力边界 | 已覆盖 / 间接支持 / 未覆盖 / 未公开四类清晰分区，用颜色或图标区分，不混在一列 |
| 流程机制 | 箭头可见且居中于步骤之间；步骤框等宽；AI 与人工分工用泳道或颜色标注 |
| 架构分层 | 各层边界清晰；连接线指向正确无交叉；层级方向（上→下或左→右）全程一致 |
| 截图实证 | 截图保留完整界面语境；关键区域有编号或线框标注；标注旁有"看到什么、说明什么"解释 |
| 数据趋势 | 轴标签可读；图例在底部用主题色；takeaway 条单行加粗；关键数据标口径和来源 |
| 原因分析 | 根因链各层有证据支撑，不只写抽象原因；因果箭头方向正确 |
| 路线图 | 阶段 / 交付物 / 时间 / 负责人 / 状态字段完整；里程碑标注清晰 |
| 风险对策 | 风险 / 影响 / 对策 / 责任人 / 时间字段完整；高风险行高亮 |
| 下一步与决策 | 行动 / Owner / 时间 / 验收标准 / 待决策项分区清晰；待决策项视觉突出 |
| 核心结论 | 2—4 条结论分栏或分区，每条有独立标题，不堆叠成长段落 |
| KPI / 大数字 | 大数字视觉主导（≥32pt，见 `visual-system.md` §2 token）；数字旁有单位和口径 |

### C. 技术与编辑性

- 无溢出、遮挡、裁切和错误连接线；
- 无异常断词、孤行、单词中间换行或品牌名拆分；
- 全部文字符合 `visual-system.md` §2 的文字设计 token：各类型不低于其下限值，同一类型跨页字号、颜色、字重一致；
- 标题框按单行设计时未换行，两行标题按语义显式断行；
- 行列内容为原生表格，图表为原生图表；
- 语义模块可组合、可取消组合，无 `noGrp`/`noUngrp` 锁；
- 可编辑性、可组合性、可取消组合性与二次编辑的便利度视为验收标准，而非可选的润色；
- 中文使用 `Noto Sans CJK SC`，渲染无拉丁回退；
- 最终 PPTX 可被严格 Open XML 读取器打开并正常渲染。
- 使用 `node scripts/inspect-pptx.mjs --pptx final.pptx --plan slide-plan.json --json qa-structure.json` 校验页数、原生图表/表格、备注来源、语义分组和分组锁；任何 error 都阻断交付。

### D. 事实与来源

- 数字、单位、时间、版本、样本和口径正确；
- 产品名、公司名、术语、日期和链接正确；
- 页内短来源与备注完整来源一致；推断未写成事实；
- 人工占位项的 ID、责任、格式、阻断级别和到位后动作完整，无泛化占位语残留。

### E. Deck 整体检查

在 A—D 轮逐页通过后，对整套 deck 做整体级 pass/fail 检查。这不是品味评分，而是机械规则。

**版式多样性**：

- 10 页以内的 deck 至少使用 4 种宏观版式（按视觉轮廓计数，不按页型 ID）；
- 11—18 页的 deck 至少使用 5 种宏观版式；
- 不连续 3 页使用相同的卡片/网格/表格结构；
- 缩略图看起来像一个重复模板包时，重新映射部分页面再打磨。

**章节与锚点**：

- 每个主要章节至少包含 1 个锚点页——有清晰视觉中心的大图/大流程/大结果/大总结；
- 数据或实验章节不能只由表格和文字卡片组成，至少 1 个主结果证明页；
- 方法或方案章节必须包含框架/机制/流程/模块关系图，不能只命名组件。

**标题与角色**：

- 是否有标题空洞、通用或可互换——能与另一个 deck 的标题互换说明太通用；
- 是否有页面重复前一页信息而没有新增叙事角色；
- 结果页是否有 takeaway、亮点或含义，而不只是展示数据；
- 方法页是否解释了信息流、组件关系或因果链，而不只是罗列部件；
- 总结页是否重新连接了问题、方法、证据和含义。

**失败处理**：E 轮任一项失败时，先判断是实现缺陷还是已确认方案不可实现。实现缺陷只修改 `slide-plan.json` 或适配器；改变页型、载体、信息、主张或页数时，标记下游失效并路由回 `$huawei-deck-script`。修复后重新生成并重跑 A—E。

## 7. 交付规则

- 交付最终通过 QA 的 PPTX、`deck-state.md`、已确认阶段产物、`sources.md` 与 `qa-report.md`。用户界面优先突出 PPTX。
- 内部迭代文件（sample-v2、final-v3 等）放入单独临时目录，不暴露给用户；只提升一个通过验收的 release candidate 为最终文件。
- 交付说明包含：所选引擎与检测依据、相对逐字稿的版式性偏差、实际渲染字体、未补占位项清单（区分阻断与非阻断：页面、ID、责任角色、请求材料、期望格式、支持的结论、到位后动作）、QA 结论。
- 按当前宿主的文件交付机制提供用户可访问的绝对路径。

## 8. QA 失败修复配方

五轮 QA 任一项失败时，先查下表找到对应修复动作，再修改生成脚本、重新生成、重跑受影响轮次。不通过主观重新设计解决。

### 逐页级修复

| 失败现象 | 修复动作 |
|---|---|
| 标题空洞、通用或可互换 | 改写为"主题 + 具体结论"。如"市场分析"→"AWS 覆盖生成、校验和评分，定价与交付配置仍由卖家完成" |
| 一页太挤、内容溢出 | 拆成 2 页或换更高效的页型（表格替代卡片、图表替代数字列表），不缩字号 |
| 页面无证明对象 | 从来源拉图 / 表 / 流程 / KPI / 时间线 / 矩阵 / 对比；无可用素材时转为架构分层或总结页型 |
| 实验或数据页像数据堆砌 | 加 takeaway 条 / 高亮最佳行或系列 / 拆成表格 + 图表两页 |
| 方法或方案页只列组件 | 重建为信息流 / 模块关系 / 管道 / 因果链，用流程机制或架构分层页型 |
| 视觉层级平坦——所有元素等权重 | 选一个元素提升（1.5 倍尺寸 / 加粗 / 华为红），其余降级（缩小 / 常规 / 次文字色） |
| 看起来像 AI 生成的文字堆砌 | 用结构化页型（前后对比 / 流程机制 / 方案决策表）替代纯文字页；嵌入真实截图而非占位 |
| 右对齐标签被裁切 | 缩短文字或加宽容器，不缩小字号 |
| 卡片高度或宽度不均匀 | 用公式计算位置而非硬编码，确保同行卡片等宽等高 |
| 图片模糊或填充不足 | 提高源图分辨率；默认用 contain 保持比例；必须铺满时先按目标框比例预裁切，标记 `preparedForFrame: true`，不要依赖引擎默认 cover 裁切 |
| 自定义布局（受控升级）QA 失败 | 保留内容，回退到最近的默认页型，再加至多一个局部组件 |

### Deck 级修复（E 轮失败）

| 失败现象 | 修复动作 |
|---|---|
| 连续 3 页卡片 / 网格 / 表格 | 将其中一页换成锚点页型（截图实证 / 数据趋势 / 流程机制 / 路线图 / 大数字） |
| 缩略图看起来像重复模板包 | 重新映射双轴逐字稿的页型选择，在需要锚点的章节加大图 / 大流程 / 大结果 / 大总结 |
| 总结页没有闭合论证 | 重写为连接问题 / 方法 / 证据 / 含义，用核心结论页型而非又一个卡片列表 |
| 商业汇报用了中性话题标题 | 将重要标题改为结论式——说明什么变了、为什么重要、需要什么决策 |
| 学术或研究材料太商业 | 恢复清晰的研究导航（研究问题 / 方法 / 发现 / 影响），减少推销措辞，保持话题标题具体 |

### 升级为结构性问题

同一页面经 3 次修复迭代后问题仍存在，问题很可能是结构性的而非外观的：

- 用了错误的页型——换页型，不要在不适合的页型上反复调像素；
- 页面过载——拆成 2 页；
- 内容本身不清晰——返回 `$huawei-deck-script`，重新确认该页表达意图和证明对象。

不要带着结构性问题继续打磨像素。
